## 🔴 Vulnerabilidade crítica encontrada

### Vazamento da tabela `customers`

**Arquivo:** `supabase/migrations/20260403140000_driver_app_columns.sql`

```sql
CREATE POLICY IF NOT EXISTS "customers_select" ON customers
  FOR SELECT TO authenticated USING (true);   -- ⚠️ libera tudo
```

**Problema:** Postgres avalia múltiplas policies em **OR**. Bastava `customers_select` retornar `true` pra liberar SELECT, anulando policies restritivas (`Customers can view own data`, `Establishments can view their customers`).

**Impacto pré-fix:** qualquer usuário autenticado podia listar:
- Nome completo
- Email
- Telefone
- CPF
- Endereço

de **todos os clientes** da plataforma. Violação de:
- LGPD art. 6, III (necessidade — só dados estritamente necessários)
- LGPD art. 46 (medidas técnicas de segurança)

**Provável intenção:** drivers verem dados do cliente do pedido que vão entregar. Mas o jeito correto é via JOIN com `orders` (driver vê só customer dos `assigned_orders` dele), não liberar a tabela inteira.

**Fix aplicado:** `supabase/migrations/20260608000000_rls_audit_fix_customers_leak.sql`
- DROP POLICY `customers_select`
- Migration falha (RAISE EXCEPTION) se a policy persistir, evitando rollback silencioso
- Comentário com policy alternativa pra drivers (via JOIN com orders.driver_id) deferida até consolidação do schema driver-orders

## ⚠️ Itens pra revisar manualmente

### `payment_splits` / `payment_split_items` / `mp_transactions`

RLS habilitada mas sem policy explícita encontrada via grep. Default deny faz com que **só `service_role`** (edge functions) acesse. Isso é **seguro**, mas:

1. **Member dashboard do prestador**: se a UI vai mostrar histórico de splits (escrow_state, available_at, etc.) precisa de policy do tipo:
   ```sql
   CREATE POLICY "merchants_view_own_splits" ON public.payment_split_items
     FOR SELECT TO authenticated USING (
       establishment_id IN (
         SELECT id FROM public.establishments WHERE owner_id = auth.uid()
       )
     );
   ```

2. **Customer ver histórico próprio de pagamentos**: similar via JOIN orders.

Recomendação: implementar policies sob demanda quando member dashboard for adicionar leitura desses dados. Hoje frontend usa edge functions (service_role) que já bypassa RLS.

### Outras tabelas

- ✅ `establishments`: policy `Owner can manage` via `owner_id = auth.uid()` — OK
- ✅ `reviews`: policy `Users can create reviews for their orders` com `auth.uid() = user_id OR user_id IS NULL` — OK pra reviews anon
- ✅ `coupons`: leitura pública apenas de `is_active=true` — OK

## Re-auditoria pré-go-live (2026-05-12)

Análise das 11 migrations de 2026 antes do go-live pegou 2 vazamentos adicionais nas tabelas de sync LocalizAI:

| Tabela | Política | Vazava | Severidade |
|---|---|---|---|
| `localiza_sync_log` | `USING (true)` | Histórico de sync + erros para qualquer authenticated | Crítico |
| `localiza_place_mapping` | `USING (true)` | Mapeamento estabelecimento → place_id externo | Crítico |

Combinadas, as duas permitiam enumeração completa da base de merchants. Já cobertas pela owner-scoped policy `localiza_place_mapping_owner_select`, então só precisaram ser removidas + substituídas por admin-only.

3 funções `SECURITY DEFINER` sem `SET search_path` (CVE-2018-1058 pattern):
- `get_localiza_sync_status()`
- `get_localiza_products(TEXT)`
- `get_localiza_reviews(TEXT)`

**Fix aplicado:** `supabase/migrations/20260618000000_rls_hardening_localiza_sync.sql`
- DROP policies open + CREATE admin-only via `public.has_role()`
- `ALTER FUNCTION ... SET search_path = public` para as 3 funções
- Assertion final que falha o deploy se policies open ainda existirem (anti-rollback silencioso)
